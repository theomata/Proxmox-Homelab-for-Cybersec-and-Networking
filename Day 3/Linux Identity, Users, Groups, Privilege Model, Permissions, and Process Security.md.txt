# Core Linux Security Mental Model

Linux is a multi-user operating system.

Everything is tied to identity.

A system does not simply “run commands.”

Linux evaluates:

```text
User
↓
Group
↓
Permissions
↓
Ownership
↓
Process Identity
↓
Authorization
↓
System Access
```

If you understand this chain, Linux behavior becomes logical.

---

# SECTION 1 — Users

## Definition

A user is a Linux-recognized identity.

Examples:

- theo
- root
- www-data
- mysql
- syslog
- nobody

Not all users are humans.

Many are service accounts.

---

# Why service accounts exist

Example:

Apache web server.

If Apache runs as root:

Compromise Apache  
→ attacker gains root

Very bad.

Instead:

Apache may run as:

```bash
www-data
```

Now:

Compromise Apache  
→ attacker inherits limited service privileges

This is called:

## Privilege Separation

A critical Linux and cybersecurity principle.

---

# SECTION 2 — Root

Root is the Linux superuser.

UID = 0

Root bypasses almost everything.

Root can:

- read any file
- kill any process
- create users
- delete system files
- modify firewall
- configure routes
- bind privileged ports
- mount disks
- change ownership
- disable protections

This is why:

## Least Privilege matters.

Never operate as root unless required.

# SECTION 4 — id

## Command

```bash
id
```

### Sample Output

```bash
uid=1000(theo) gid=1000(theo) groups=1000(theo),27(sudo),4(adm)
```

---

## Breakdown

### uid=1000(theo)

User identity number.

Kernel trusts UID more than name.

---

### gid=1000(theo)

Primary group.

---

### groups=1000(theo),27(sudo),4(adm)

Supplementary groups.

Extra inherited permissions.

---

# Why this matters

Compromised account = inherited permissions.

If attacker compromises user in:

- sudo
- docker
- adm

Potential privilege escalation.

---

# SECTION 5 — Groups

Check:

```bash
groups
```

### Sample Output

```bash
theo sudo adm cdrom dip plugdev lxd
```

Groups act as permission buckets.

Instead of assigning permissions per user.

This scales administration.

---

# Security Relevance

Bad group membership = dangerous.

Example:

docker group often nearly root-level.

Why?

Docker can mount host paths.

# SECTION 6 — /etc/passwd

## Command

```bash
cat /etc/passwd | tail -10
```

### Sample Output

```bash
syslog:x:104:110::/home/syslog:/usr/sbin/nologin
mysql:x:111:115:MySQL Server,,,:/nonexistent:/bin/false
theo:x:1000:1000:Theo:/home/theo:/bin/bash
```

---

# Structure

```text
username:password_marker:UID:GID:comment:home:shell
```

---

## Example

```bash
theo:x:1000:1000:Theo:/home/theo:/bin/bash
```

Field breakdown:

| Field | Meaning |
|------|------|
| theo | username |
| x | password stored elsewhere |
| 1000 | UID |
| 1000 | GID |
| Theo | description |
| /home/theo | home |
| /bin/bash | shell |

---

# Why admins care

Audit accounts.

Find:

- service users
- shell access
- disabled logins

---

# Why attackers care

Enumerate:

- privileged users
- shells
- attack targets

# SECTION 11 — chmod

Change permissions.

## Numeric method

```bash
chmod 600 secrets.txt
```

Meaning:

Owner:
rw-

Group:
---

Others:
---

---

## Common values

### 777
rwxrwxrwx  
Dangerous.

### 755
rwxr-xr-x  
Common directories.

### 644
rw-r--r--  
Common files.

### 600
rw-------  
Private files.

### 700
rwx------  
Private directories.

---

# SECTION 12 — chown

Change owner.

```bash
sudo chown analyst:analyst report.txt
```

Now file belongs to analyst.

Critical in service isolation.

---

# SECTION 13 — chgrp

Change only group.

```bash
sudo chgrp adm logs.txt
```

Useful when ownership remains same.

---

# SECTION 14 — umask

Check:

```bash
umask
```

Sample:

```bash
0022
```

Default permission mask.

Controls new file defaults.

---

# Logic

Requested:
666

Mask:
022

Final:
644

# SECTION 15 — Sticky Bit

Seen in:

```bash
ls -ld /tmp
```

Sample:

```bash
drwxrwxrwt
```

`t` = sticky bit.

Users can only delete their own files.

Critical in shared directories.

---

# SECTION 16 — setuid

Can allow executable to run as file owner.

Check examples:

```bash
find / -perm -4000 2>/dev/null
```

May show:

```bash
/usr/bin/passwd
```

Security implication:

setuid abuse = privilege escalation vector.

---

# SECTION 17 — setgid

Check:

```bash
find / -perm -2000 2>/dev/null
```

Can force group execution or inheritance.

Useful and dangerous.

---

# SECTION 22 — sudo Flow

When running:

```bash
sudo apt update
```

Flow:

User  
↓  
sudo request  
↓  
PAM auth  
↓  
sudoers policy  
↓  
temporary root execution  
↓  
return to user

Controlled elevation.

# SECTION 24 — Troubleshooting Methodology

## Problem: Permission denied

Check:
- ownership
- chmod
- group

Commands:

```bash
ls -l
id
groups
```

---

## Problem: sudo fails

Check:

```bash
sudo -l
groups
```

Likely sudo membership issue.

---

## Problem: service running but app unreachable

Check:

```bash
ss -tulnp
ip a
ip route
systemctl status <service>
```

Could be:
- wrong bind address
- firewall
- service crash
- route issue

---

## Problem: unknown process spike

Check:

```bash

htop
ps aux --sort=-%cpu | head
```
